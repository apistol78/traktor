1Overview

The Vulkan backend implements IRenderSystem as RenderSystemVk and IRenderView as RenderViewVk. Nothing above those two classes sees Vulkan. On the build thread the render graph turns passes into render blocks inside a RenderContext. The render thread replays those blocks against the view, and each block becomes a few calls such as beginPass, draw, compute, barrier or waitAsynchronousCompute. The view records the calls into per-frame command buffers and submits them.

At a glance

API level
Vulkan 1.2 instance and device. Shaders are GLSL, compiled offline by glslang to SPIR-V 1.5 and optimized with spirv-tools (ProgramCompilerVk, editor only).
Queues
One graphics queue, plus one queue from a compute-only family when the device has one. Without such a family, "asynchronous" work goes to the graphics queue. Presentation uses the graphics queue unless the surface needs another family.
Frames in flight
One Frame slot per swap chain image; three images are requested. The acquired image index selects the slot, and beginFrame blocks only on that slot's previous submissions.
Command buffers
Primary and one-time-submit, allocated from transient pools that each Queue keeps per thread; uploads have a pool of their own. Every CommandBuffer owns one fence.
Cross-queue sync
A timeline semaphore per view orders asynchronous compute before graphics; a timeline semaphore per device orders uploads before work on other queues. Binary semaphores handle acquire and present.
Uploads
Deferred lambdas are recorded into one command buffer on the graphics queue, normally at endFrame. The CPU does not wait for it: the command buffer is released once its epoch has completed, and work on other queues waits on the upload timeline instead.
Destruction
Two fences in series. The ResourceMorgue keeps a released object for three frames on the CPU; then Context defers the Vulkan destroy until the GPU has consumed every submission that could still use it.
Binding model
A per-program descriptor set 0 (dynamic uniform buffers, samplers, non-bindless images, storage buffers, acceleration structures) plus three global bindless sets of 16536 entries each, allocated from a pool of their own.
Uniforms
Three pools by update frequency (Once, Frame, Draw) hand out fixed-size blocks in persistently mapped buffers; they are bound with dynamic offsets. A released block is reused once the submissions issued before its release have completed.
Passes and pipelines
Classic VkRenderPass and VkFramebuffer objects, created on demand and cached; render passes are shared by all views. Pipelines are created at first use, keyed by render pass handle, and kept in a VkPipelineCache that is saved to disk.
Image layouts
Tracked on the CPU per mip and layer. Each transition's barrier is derived from the old and the new layout.
GPU timers
Timestamp queries in one 4096-query segment per frame slot. Results are read when the slot comes round again.

Rules the backend relies on

These come up again in the sections that explain them; they are listed here because code outside code/Render/Vulkan has to follow them.

  1. Record and submit a view only from the thread that rendered its first frame (§14).
  2. Anything that submits frame work before endFrame calls Context::performUploads first (§8).
  3. Code that records into a view's command buffers directly, such as a render plugin, calls RenderViewVk::invalidateBindings afterwards (§4).
  4. A resource that the CPU or the asynchronous queue rewrites every frame while graphics reads it must be ring-buffered deeper than the frames in flight (§6, §7).
  5. A resource whose Vulkan handle changes between frames must be part of ProgramVk's descriptor-set key (§10).
  6. Vulkan handles are released only through Context::addDeferredCleanup; a resource's destroy() never frees GPU objects itself (§9).
  7. Asynchronous compute passes never consume graphics output from the same frame (§7).
  8. GPU results are read through BuReadBack buffers with the caller's own sentinel and ring; nothing fences a read-back (§10).
  9. Time query results are one slot rotation old, so a frame must issue its queries in the same order every time (§13).

2Architecture and ownership

RenderSystemVk owns the device-level objects and one Context. The context is shared by every view and every resource: it owns the queues, the upload and cleanup machinery, the descriptor pool and the pipeline map. Each RenderViewVk owns a surface, a swap chain and one Frame per swap chain image.

Resources are handed out as interfaces (Buffer, ITexture, IRenderTargetSet, IProgram, IAccelerationStructure, IVertexLayout). Their Vulkan objects live in two private primitives: ApiBuffer (a VkBuffer and its VMA allocation) and Image (a VkImage, its views, their bindless indices and the tracked layouts). Both hand their handles to Context::addDeferredCleanup when destroyed.

Runs once per process, in this order:

  1. Load the Vulkan loader and resolve the core entry points (initializeVulkanApi): vulkan-1.dll on Windows, libvulkan.so.1 on Linux, libvulkan.so on Android, libMoltenVK.dylib on macOS.
  2. Create the instance with API version 1.2. Extensions: the platform's surface extensions, VK_EXT_debug_utils, VK_KHR_get_physical_device_properties2, on Windows and Linux also VK_EXT_swapchain_colorspace, plus whatever XeSS asks for. Reset, loss and close

  • reset(width, height) waits for the device to go idle, marks the view lost, drops pending window events, marks every frame and flying command buffer as consumed with externalSynced() (flying ones become spares), destroys the primary targets, drains ResourceMorgue::flush and Context::performCleanupAll, and runs create again. The old swap chain's image-available semaphores can still hold a signal nobody will consume (VUID-vkAcquireNextImageKHR-semaphore-01779), so they are parked in m_retiredImageAvailableSemaphores until close().
  • If the new swap chain has a different number of images, all frames and the query pool are rebuilt.
  • A failed vkAcquireNextImageKHR or vkQueuePresentKHR (any result other than SUCCESS or SUBOPTIMAL_KHR), or a failed fence wait, posts RenderEventType::Lost and sets m_lost. beginFrame and beginPass then return false until the owner resets the view.
  • close() waits for the device, performs pending uploads and waits for them, saves the pipeline cache, drains the morgue and all cleanups, waits for every command buffer, then destroys frames, semaphores, the query pool, the swap chain, the retired semaphores, the surface and the window.
  • On Windows the view coalesces WM_SIZE into a single Resize event (only when the size differs from the swap chain), turns WM_CLOSE into Close, Alt+Enter and Ctrl+Enter into ToggleFullScreen, and keeps the window at least 320 × 200.

Queue

Vulkan requires external synchronization of a VkQueue, so Queue::submit and Queue::present hold Queue::m_lock around vkQueueSubmit and vkQueuePresentKHR. submit also enforces upload ordering for every queue except the graphics queue (§8): it reads the latest upload value while holding the graphics queue's lock and, if this queue has not waited on that value yet, appends a wait on the upload timeline semaphore at ALL_COMMANDS. Any timeline submit info already on the submission is merged, with wait value 0 for binary semaphores. The last value waited is kept in m_uploadValueWaited, because one wait also orders everything submitted after it. supportsGraphics() reports whether the family has GRAPHICS, which barrier needs to pick legal stages (§12).

Command pools

Command pools need external synchronization, so every thread records from a pool of its own. Each Queue keeps a map from thread id to pool, guarded by m_commandPoolsLock; a thread's pool is created with RESET_COMMAND_BUFFER and TRANSIENT the first time it acquires a command buffer from that queue, and the queue destroys its pools when the device goes away. A command buffer can therefore only be recorded, reset and submitted on the thread that allocated it, which CommandBuffer asserts.

The upload command buffers are the one exception. Whichever thread flushes the uploads records them, and whichever thread notices they have been consumed releases them, so they come from a pool of their own (Queue::createCommandPool, owned by the context) that the graphics queue lock guards.

CommandBuffer

Queue::acquireCommandBuffer(tag) allocates a primary command buffer from the calling thread's pool, or from the pool passed in, names it, begins it with ONE_TIME_SUBMIT and wraps it in a CommandBuffer that creates an unsignalled fence. Every submit ends the buffer, takes a submission epoch (§5) and goes through Queue::submit. The general form, submit(waits, waitCount, signals, signalCount), takes any mix of binary and timeline semaphores; it always attaches one timeline submit info that covers every wait and signal, since values of binary semaphores are ignored. The others are shorthands for it:

  • submit(waits, stages, signal) with binary semaphores, used at endFrame.
  • submitSignal(semaphore, value) signals a timeline value, used for compute batches and uploads.
  • submitWait(semaphore, value, stages) waits for a timeline value, used for graphics splits.

wait() blocks on the fence without a timeout and then calls Context::endSubmission, which resets the fence under the submission lock. externalSynced() does the same bookkeeping without waiting, for use after vkDeviceWaitIdle. reserveSubmission() takes the epoch before recording has finished, so that cleanups queued while the buffer is being recorded wait for it; only the upload buffer uses it. getSubmissionEpoch() returns the reserved epoch while recording and the submitted epoch while in flight, which lets code that records into an upload note which epoch has to complete before its memory may be reused. Destroying a command buffer that is still in flight is a fatal assert.

Frame command buffers

Each Frame has one graphics and one compute command buffer. They are created lazily in the first beginFrame, which ties them to the render thread's pools, and then reused: wait, reset, record, submit. When the frame is split in the middle (§7), the submitted buffer moves to flyingGraphicsCommandBuffers or flyingComputeCommandBuffers and recording continues in another one. The next time the same slot begins a frame, the flying buffers are waited for and moved to spareGraphicsCommandBuffers and spareComputeCommandBuffers, and later splits reset and reuse the spares before allocating new ones. A frame that splits the same way every time therefore allocates nothing after warm-up.

Bind caches remember which pipeline, vertex and index buffer are bound. The compute caches also remember which command buffer they were bound in, so a split never skips a bind into the new buffer. invalidateBindings() forgets everything; beginFrame and endFrame call it, and so must any code that records into the view's command buffers directly, as the XeSS plugin does.

Submission epochs

The cleanup system needs to know whether every submission issued so far has been consumed, independently of which queue or thread issued it. Context numbers submissions:

  • beginSubmission(fence) assigns the next epoch and appends {epoch, fence, issued = false} to m_inFlightSubmissions.
  • submissionIssued(epoch) sets issued once vkQueueSubmit has returned. Until then the fence belongs to the submitting thread and must not be polled.
  • endSubmission(epoch, fence) resets the fence and removes the entry, both under the submission lock.
  • getCompletedEpoch() retires entries from the front while they are issued and their fence reports VK_SUCCESS, then returns the front epoch minus one. A view that stops rendering never waits on its last command buffer, so retiring by polling keeps cleanups from being held back indefinitely.

Guarantees the code relies on

  • Barrier scopes extend across submissions on the same queue. The upload buffer ends with an ALL_COMMANDS to ALL_COMMANDS memory barrier, which orders it before all later work on the graphics queue.
  • A signal defined by vkQueueSubmit covers every command submitted earlier to the same queue. The specification says so explicitly for semaphore signals, and fence signals defined by vkQueueSubmit have the same scope. Waiting on any fence therefore also waits for everything queued before it, and a completed epoch means every submission numbered before it has completed too.
  • A semaphore wait blocks the submission that carries it and, through queue order, everything submitted after it. Nothing ever makes the compute queue wait for graphics, so the only thing keeping a frame's graphics work from running alongside an asynchronous batch is a wait that is submitted ahead of that work (§7).
  • Timeline values only grow, and a wait for v is satisfied by any later signal of a value ≥ v. That is why all asynchronous work recorded between two flushes can share one value, and why a value that was reserved but never signalled is harmless.
  • Binary semaphores are reused only after the wait on their previous signal is known to have executed (Figure 6).

6The frame loop

In the runtime, Application builds and renders on two threads. The main thread runs IState::build, which runs the render graph into a RenderContext. The render thread, Application::threadRender, waits for a built frame and then calls beginFrame, IState::render (which replays the context), endFrame and present. RenderServer::getThreadFrameQueueCount() returns 2, so two contexts alternate, and the main thread waits up to one second for the render thread to finish the previous frame before it hands over the next. In the editor both roles run back to back on the UI thread.

beginFrame

  1. Return false while the view is lost.
  2. ResourceMorgue::advance() deletes the objects retired three advances ago (§9). Doing it first lets the Vulkan objects they release be picked up by this frame's cleanup.
  3. Increment the frame counter and pass it to vmaSetCurrentFrameIndex.
  4. vkAcquireNextImageKHR with no timeout, signalling the spare semaphore. The returned index i selects Frame i. Failure posts Lost.
  5. Swap the spare semaphore into slot i (Figure 6).
  6. Wait for the slot's flying command buffers and keep them as spares for this frame's splits.
  7. Wait for the slot's graphics command buffer from its previous use, then reset it (or create it on first use). The same for the compute command buffer. The profiler shows these waits as "Wait graphics queue" and "Wait command queue".
  8. Read back the timestamps the slot wrote last time and reset its query segment from the host (§13).
  9. Reset the statistics, forget every cached binding, and reset the asynchronous batch state: no open batch, and the submitted and waited values set to the current timeline value.

Recording

  • Every frame caches the bound graphics pipeline, vertex buffer view and index buffer view, and skips rebinding when a draw uses the same ones. The caches are cleared at beginFrame, at endFrame and whenever the graphics command buffer is replaced.
  • A draw first compares its pipeline key with the view's most recently used pipeline and otherwise looks up or creates the pipeline (§11). It calls ProgramVk::validate to upload uniforms and bind descriptor sets (§10), binds buffers, and records vkCmdDraw or vkCmdDrawIndexed with vertex offset and first instance 0.
  • A dispatch uses the compute pipeline the program keeps and binds it unless it is already bound in the same command buffer. It validates the program with the compute bind point, which also moves render targets bound as storage images to GENERAL when recording on the graphics queue (§12), and records vkCmdDispatch with the work size divided by the local work group size, rounded up. computeIndirect only exists on the graphics queue.
  • copy() moves the source to TRANSFER_SRC and the destination to TRANSFER_DST, records vkCmdCopyImage and restores both previous layouts.

endFrame and present

  1. endFrame clears the bind caches and calls Context::performUploads(), which submits the queued uploads without waiting for them (§8). Being submitted first, they execute ahead of the frame's graphics work.
  2. It moves the primary colour target to PRESENT_SRC_KHR.
  3. It submits the compute command buffer, signalling computeFinished.
  4. It submits the graphics command buffer, waiting for imageAvailable[i] at COLOR_ATTACHMENT_OUTPUT and signalling renderFinished, and registers the frame as submitted with Context::frameSubmitted.
  5. present queues vkQueuePresentKHR, waiting for both semaphores.
  6. It calls Context::performCleanup(), which destroys what the GPU has finished with and keeps the rest for a later frame, without waiting (§9).
  7. It calls Context::recycle(), which hands back the uniform blocks whose release has been consumed by the GPU (§10).

Invariant

The number of frames in flight is the swap chain image count: three by request, but the driver may create more. beginFrame waits only for the acquired slot, and modes such as MAILBOX or IMMEDIATE do not promise round-robin acquisition. Anything the CPU or the compute queue rewrites every frame while graphics may still read an older copy must be ring-buffered deeper than that. The count is per view: a resource that every view rewrites, such as the world's top level structure or a skinned mesh's skin, needs frames in flight times views. Current rings: 12 slots per BufferDynamicVk, 6 for skinned and deformed vertex buffers, and acceleration structures, which start with 4 slots and grow on demand (§7).

Acquire semaphore rotation

A binary semaphore handed to vkAcquireNextImageKHR must not have a pending signal or wait. The image index is not known until the call returns, so the view cannot pick the image's own semaphore up front. It keeps one semaphore per image plus a spare: the acquire always signals the spare, which is then swapped into the acquired image's slot.

7Asynchronous compute

Callers put work on the asynchronous queue by passing asynchronous = true to compute, writeAccelerationStructure, barrier, beginTimeQuery/endTimeQuery and the marker calls. RenderViewVk records such work into Frame::computeCommandBuffer. On a device with a compute-only family that buffer goes to the dedicated queue; otherwise it goes to the graphics queue, and the same calls turn into barriers.

Batches and handles

  • The first asynchronous dispatch or acceleration structure build after a flush reserves a timeline value (openComputeBatch, ++m_timelineSemaphoreValue). Everything recorded until the next flush shares that value.
  • signalAsynchronousCompute() closes the batch and returns ComputeHandle{value}. With nothing recorded since the last flush it returns the last submitted value, so a later wait still covers earlier work.
  • waitAsynchronousCompute(handle) makes later graphics work observe the batch. Values at or below Frame::graphicsWaitedValue are skipped, and an invalid handle is ignored.
  • synchronize() flushes both command buffers with a fresh value that compute signals and graphics waits for.
  • A handle is only valid within the frame that produced it.

Invariant

submitWait attaches the wait to the submission that carries the work recorded before the waitAsynchronousCompute call, and that is deliberate. On a dedicated queue that work (G0 above) therefore also waits for the batch, although it does not consume its results. Nothing makes the compute queue wait for graphics, so this wait is the only thing that keeps G0 from executing concurrently with C0. The render graph declares only which graphics passes consume asynchronous outputs; the passes recorded before the wait may still touch what the batch reads or rewrites, and they rely on the batch having finished first. synchronize() behaves the same way.

The cost shows only when the GPU is idle at the start of a frame, which puts the frame's first graphics work behind compute; when the graphics queue is still busy with earlier frames it costs nothing, since the compute batch was submitted long before. Submitting G0 without the wait and attaching it to the next graphics submission was tried. It lost the device within seconds of the 3D scene appearing in the Zombie main menu, with no validation message beforehand, and with the wait put back the fault has not recurred. Removing the stall safely needs a graphics → compute dependency: a graphics timeline signalled by each graphics split and waited on by the next compute batch.

Render graph integration

  • Passes created with RenderPass::Queue::AsyncCompute are built between RenderContext::beginAsyncCompute and endAsyncCompute; compute blocks added in that scope are tagged asynchronous. Build code checks renderContext->isAsyncCompute(). Today's asynchronous passes are "Skinned mesh skin", "Skinned mesh AS", "Static mesh deform", "Static mesh deform AS", "Instance mesh deform", "Instance mesh deform AS" and "RT world setup" (the TLAS build).
  • After each asynchronous pass RenderGraph::build appends a SignalComputeRenderBlock and merges the pass's blocks into the render queue at once, so they are recorded, and on a dedicated queue submitted, early.
  • RenderGraph::validate puts one WaitComputeRenderBlock before the earliest graphics consumer of each asynchronous pass; a wait covers everything recorded before its signal, so later consumers need nothing. A consumer on the asynchronous queue gets three barriers instead: Compute → Compute, Compute → AccelerationStructureUpdate, and AccelerationStructureUpdate → AccelerationStructureUpdate | Compute. An asynchronous pass without a known consumer is waited for right after it.
  • A pass that waits starts a new render pass, because a queue split cannot happen inside one.
  • An asynchronous pass may not consume graphics output from the same frame, since the compute queue never waits for graphics. validate asserts this in debug builds.

Invariant

A wait orders compute before graphics within one frame only. Frame F+1's compute work can run while frame F's graphics work still reads the previous results, so everything the asynchronous queue rewrites per frame is ring-buffered: the TLAS and dynamic BLAS (AccelerationStructureVk), and 6 slots for skinned and deformed vertex buffers. ProgramVk includes the current acceleration structure handle in its descriptor-set key, so a cached set never points at a slot that is being rebuilt.

Acceleration structure rings

A fixed ring depth is not enough for acceleration structures. The world's top level structure belongs to its RTWorldComponent, so every view rendering that world rebuilds the same structure, and so does every probe capture face rendered within a frame. Skinned and deformed meshes refit their bottom level structures once per view as well. On top of that the asynchronous queue can trail the CPU by all frames in flight, since its batches wait on the upload timeline behind the graphics work queued ahead of the uploads. With two views each rebuilding the world every frame, a 4-slot ring came round while an earlier build was still pending, and the CPU rewrote the instance data under it. The build then read instances of a later frame, whose bottom level structures might not have been built yet, and NVIDIA's build shader failed with a misaligned address.

So AccelerationStructureVk::advance only rewrites a slot when no work can read it any longer, and otherwise inserts a fresh slot into the ring:

  • When a slot stops being current, it notes how many frames have been submitted so far. Views register every frame at endFrame, after its last submission (Context::frameSubmitted), and the context remembers the issued epoch of the last 64 frames.
  • Views render one after another, so the first frame submitted after the slot was left is the frame that left it. Once that frame has been submitted, every reader of the slot has been, and the slot is free when the epoch issued with that frame has completed.
  • A slot left by the frame still being recorded is never free: its readers may sit in command buffers that have not been submitted, so waiting for them would never end. A slot that is not free gets a new slot inserted in front of it. Top level slots are created at once, with instance, hierarchy and scratch buffers of their own; bottom level slots get their buffers when first built, which is then a full build rather than a refit.
  • Rings therefore grow to what the views, probe captures and GPU lag need. In the Zombie gameplay stage, rings started at one slot grew to five. Each growth is logged at debug level.

Resources cross families without ownership transfers. When the graphics and compute families differ, ApiBuffer creates buffers with CONCURRENT sharing, and Image does the same for images with storage usage (textures created with shader storage), which stay in GENERAL between uses. Render targets remain EXCLUSIVE and their layouts are tracked in graphics queue order, so they cannot be written by the dedicated queue: binding one as a storage image in asynchronous compute logs an error once per program and skips the layout transition. Present waits for computeFinished, so the part of the frame's compute work recorded after the last signal also completes before the image is shown.

8Resource uploads

Creating or updating a resource never records into a frame command buffer, and nothing submits a command buffer of its own any longer. A resource either writes straight into host-visible memory (dynamic, read-back and uniform buffers) or queues a deferred upload with Context::addDeferredUpload(fn, size): a lambda that records transfer work into an upload command buffer later.

When queued uploads run

  • In endFrame, before the frame's command buffers are submitted.
  • Before any submission of frame work in the middle of a frame: signalAsynchronousCompute and waitAsynchronousCompute on a dedicated compute queue, and synchronize.
  • At once, on the calling thread, when the queued uploads hold 32 MiB or more of staging memory (c_maxPendingUploadSize). The size counts static buffer data, immutable texture data and BLAS scratch buffers. A loading thread can create resources far faster than frames go by, and without the cap every staging buffer created between two frames would be alive at once.
  • At once when no view exists, as in the pipeline tools. This flush waits for the upload and then runs every cleanup, because no frame will.
  • In RenderViewVk::close, which waits for it too.

Context::performUploads

  1. Take the graphics queue lock. It is held only while recording and submitting.
  2. Release the upload command buffers of earlier flushes that the GPU has consumed (retireUploads).
  3. Swap out the queued lambdas and the pending size under m_updateLock.
  4. Acquire a command buffer from the context's upload command pool. If that fails the lambdas are put back.
  5. reserveSubmission(), so the staging buffers the lambdas release while recording are held back until this buffer has been consumed.
  6. Run every lambda: buffer copies, image transitions, copies and clears, BLAS builds. Each one releases its staging buffer, or notes the epoch when it keeps it.
  7. Record a global barrier, ALL_COMMANDS to ALL_COMMANDS, MEMORY_WRITE to MEMORY_READ | MEMORY_WRITE.
  8. submitSignal on the upload timeline semaphore with m_uploadValue + 1, then store the new value while the lock is still held.
  9. Keep the command buffer in m_uploadCommandBuffers and return. Only performUploads(true) waits: it releases the lock, waits for the fence and releases the command buffer with the lock held again.

Later graphics work is ordered after the uploads by submission order and the closing barrier. Work on other queues is ordered by the wait that Queue::submit injects (§4). That wait reads m_uploadValue under the graphics queue lock, and uploads are dequeued, recorded and submitted under the same lock, so every upload that has left the queue has also been submitted by the time the value is read.

An upload command buffer is released by whichever thread gets there first once getCompletedEpoch has passed its epoch: the next flush, or performCleanup at every present. performCleanupAll and the context's destructor wait for the device and release them all. Releasing only needs the fence to have signalled, so neither path blocks.

Performance

A flush costs the CPU only the time to record and submit. The paths that still wait are off the frame path: performUploads(true) without a view and in close, and TextureVk::lock when the GPU has not yet consumed the previous copy out of the same texture's staging buffer. A texture updated every frame therefore waits, at most, for the upload submitted at the previous endFrame, which the graphics queue runs ahead of that frame's graphics work.

Why a texture's tracked layout runs ahead

TextureVk::create and RenderTargetVk::create set the image's tracked layout to its final layout as soon as the upload is queued (Image::setVkImageLayout), and the upload lambda records its transitions with changeLayoutExplicit, starting from UNDEFINED. The upload buffer always executes before any frame work that can use the resource, so from the frame's point of view the image already is in its final layout, even while the upload is still queued. Texture updates rely on the same ordering: a texture is always in its resting layout when upload buffers execute, so unlock's copy transitions from and back to that layout without touching the tracked one.

Invariant

Any path that submits frame work before endFrame must call Context::performUploads first. A resource created during the frame has its first transfer and initial layout transition in the upload queue; frame work submitted ahead of it would see an UNDEFINED image. This was the cause of the "expects GENERAL, is UNDEFINED" crash in streaming games.

9Destruction and cleanup

When its owner lets go, a render resource can still be referenced from three places: a render context that has not been rendered yet (render blocks and program parameters hold raw pointers), a command buffer that has been recorded but not executed, and cached descriptor sets. Two mechanisms in series cover this.

Stage 1: ResourceMorgue, on the CPU

  • Buffer, ITexture, IProgram, IRenderTargetSet, IAccelerationStructure and IVertexLayout override release(). When the count reaches zero the object is retired instead of deleted.
  • retire(), callable from any thread, takes a reference and pushes the object into the current bucket. There are three buckets, one more than the runtime's frame queue depth of two.
  • advance() runs at the start of every view's beginFrame, on the render thread. It moves the head and releases the bucket it lands on, which was filled three advances ago. If something referenced the object again meanwhile (ProgramVk holds references to the textures it binds), the morgue only drops its own reference.
  • With no view registered, retire() deletes at once; tools that never render are unaffected. Removing the last view drains the queue.
  • The Vulkan resource classes' destroy() methods only relinquish ownership. Teardown happens in their destructors, which the morgue triggers.

Stage 2: deferred cleanup, on the GPU timeline

  • Destructors pass Vulkan handles to Context::addDeferredCleanup(fn, flags). The cleanup records waitEpoch, the last epoch handed out: the resource is being destroyed, so nothing new can reference it and only submissions already made can still read it.
  • present() calls performCleanup(). It computes the completed epoch and releases the upload command buffers that are done. Then, holding the graphics and compute queue locks and the cleanup lock, it runs every cleanup whose waitEpoch has completed and keeps the rest. It repeats while cleanups queue further cleanups.
  • If any cleanup that ran carried CleanupFreeDescriptorSets, every live ProgramVk (they register as cleanup listeners) drops its whole descriptor-set cache and hands the sets to a new deferred cleanup, because a cached set may reference the destroyed view or buffer. Every destroyed buffer or image thus makes every program rebuild its descriptor sets on its next use.
  • With no view, addDeferredCleanup calls performCleanupAll on the caller's thread. It waits for the device to go idle, releases every upload command buffer and runs every cleanup whose epoch has completed. With the device idle that is all of them, except cleanups held back by an upload command buffer that this very thread is recording, such as staging buffers released by the upload lambdas. Those stay queued, and the flush that is recording runs performCleanupAll again once its upload has been consumed.
  • close(), reset() and a change of swap chain image count flush the morgue and run performCleanupAll.

11Pipelines and render passes

Pipelines

  • Context::validateGraphicsPipeline looks up (primitive type, render pass handle, vertex layout hash, shader hash) in m_pipelines and calls vkCreateGraphicsPipelines with the context's VkPipelineCache on a miss. The handle identifies the render pass exactly, since render passes are shared and live as long as the pipelines. The map is guarded by m_pipelinesLock, because every thread that renders a view looks pipelines up and createProgram creates compute pipelines on loader threads.
  • Before that shared lookup, RenderViewVk compares the key with the pipeline it used last, which most consecutive draws share.
  • State comes from the program's RenderState: cull mode, front face CLOCKWISE, fill or wireframe, depth test, write and compare, stencil operations (compare and write masks are all ones), blending per colour attachment, colour write mask, alpha to coverage. The sample count comes from the target set; sample shading is enabled when multiSampleShading is above zero, except for lines; line topologies use smooth rectangular lines when the device supports them.
  • Viewport and scissor are dynamic, plus the stencil reference when stencil is enabled.
  • Compute pipelines live in a map of their own, keyed by shader hash. RenderSystemVk::createProgram creates them, so the first dispatch does not hitch, and hands them to the program, so a dispatch needs no lookup at all.
  • PipelineLayoutCache keys layouts by a hash of the bindings but compares the bindings on a hit. A collision is logged and gets a layout of its own, instead of silently sharing a wrong one.
  • Pipelines are never destroyed before the context; the collection code in endFrame is disabled.
  • The pipeline cache is loaded in Context::create from <writable folder>/Traktor/Vulkan/Pipeline.cache (~/Library/Caches/Traktor/Vulkan/Pipeline.cache on iOS) and saved in RenderViewVk::close and RenderSystemVk::purge.

13GPU timers

  • Time queries are compiled in everywhere except Android and iOS (T_USE_QUERY). At run time they need the hostQueryReset feature and a graphics family with timestampValidBits > 0. Timestamps on the asynchronous queue additionally need timestamp bits on the compute family (m_asynchronousTimeQueries).
  • The pool holds imageCount × 2 × 2048 timestamp queries and is created together with the swap chain. Slot i owns queries [i · 4096, (i + 1) · 4096).
  • beginTimeQuery(asynchronous) writes a TOP_OF_PIPE timestamp into the graphics or compute buffer and returns its index, which is always even. It returns −1 when the frame's 2048 queries are used up, or when asynchronous timestamps are not supported. endTimeQuery writes a BOTTOM_OF_PIPE timestamp at index + 1 and ignores handles that were not begun this frame.
  • In beginFrame, after the slot's fences have been waited for, vkGetQueryPoolResults reads the stamps the slot wrote last time (64-bit values with availability), then vkResetQueryPool resets the whole segment from the host.
  • getTimeQuery(q, wait, start, end) finds the slot from q and returns those resolved stamps in seconds: ticks × timestampPeriod / 109. It returns false when either stamp is unavailable. The wait argument has no effect.

Who uses them

  • Application brackets IState::render with one graphics query and reads it after present; the result is the GPU duration reported through RenderServer::setDurations.
  • RenderGraph::build, when a profiler callback is set and enabled, records a reference query around the whole graph, one query per graphics pass, and one query inside the asynchronous scope for each asynchronous pass. ProfileReportRenderBlocks at the end of the frame turn each pass's stamps into a start time relative to the reference query, shifted by the CPU time at which the graph was built, plus a duration, and pass them to the sink. The runtime forwards them to Profiler (queue 0 for graphics, 1 for asynchronous); the editor forwards them to PerspectiveRenderControl's measurements.
  • While profiling, every graphics pass ends its own render pass, so render-pass merging is disabled and the profile differs somewhat from an unprofiled frame.
  • On a shared family the asynchronous command buffer is submitted before the graphics one, so asynchronous passes show up at the start of the frame's GPU time.

Order: graphics queue → compute queue → cleanup → submission. The update lock is taken either alone or under the graphics queue lock. Queue::submit on the compute queue releases the graphics queue lock before it takes its own. A texture's staging lock sits between the graphics queue lock, under which its upload lambdas take it, and the submission lock, which lock takes to read the completed epoch; lock releases it before it waits for the GPU. The last five locks are leaves: nothing else is taken while one is held.

15Debugging aids

  • Validation. RenderSystemDesc::validation enables the Khronos layer and a messenger for validation warnings and errors, which are written to the log with the specification text on separate lines. In the runtime it is the Render.Validation setting.
  • Synchronization validation. With validation on, setting VK_KHRONOS_VALIDATION_VALIDATE_SYNC=true in the environment makes the layer report hazards, including ones between submissions, as … hazard detected lines in the log. It slows rendering enough to hide timing-dependent faults, so run without it too.
  • Device loss. The first sign is usually a failed fence wait ("Timeout while waiting on graphics command buffer to complete") followed by vkResetFences … in use; the VK_ERROR_DEVICE_LOST submissions and layout errors that follow are consequences. On Windows the System event log shows an nvlddmkm event 153 at the moment of the fault.
  • Object names. Context::setObjectDebugName names images, views, fences, semaphores, command buffers, samplers and shader modules as tag [n], with a counter per object type. Not available on Android and Apple platforms.
  • Labels. pushMarker, popMarker and writeMarker become vkCmdBeginDebugUtilsLabelEXT, vkCmdEndDebugUtilsLabelEXT and vkCmdInsertDebugUtilsLabelEXT in the graphics or compute buffer. Render blocks wrap themselves in labels named after the block, so captures show the render graph's structure. Labels are enabled when the device lists VK_EXT_debug_marker.
  • Aftermath. RenderSystemDesc::aftermath enables NVIDIA device diagnostics; RenderSystemVrfy decodes crash dumps.
  • Vrfy. code/Render/Vrfy wraps any render system and checks the API contracts. It is the reference for what an IRenderView or resource call is supposed to mean.
  • Statistics. RenderViewVk::getStatistics reports passes, draw calls and primitives per frame; RenderSystemVk::getStatistics reports live buffers, textures, target sets and programs.
  • Profiler scopes. vkAcquireNextImageKHR, "Wait graphics queue", "Wait command queue", RenderViewVk::endFrame, RenderViewVk::present, Context::performUploads, Context::performCleanup, RenderViewVk::synchronize, signalAsynchronousCompute and waitAsynchronousCompute show where the render thread blocks.

16Observations

Things noticed while reading the code for this document, and what became of them. The fixes were checked by running the Zombie runtime, main menu and gameplay stage, on a device with a dedicated compute family (RTX 5090), with the validation layer and with synchronization validation (VK_KHRONOS_VALIDATION_VALIDATE_SYNC=true). With the old code, synchronization validation reported 22 hazards in the main menu and 30 in the gameplay stage. With the new code the only hazard left in either stage is the swap-chain one listed under Open, which the old code reported too. The layer stops repeating a message after 10 reports, so counts above 10 are capped.

Open

  1. HazardA mid-frame split can transition the swap chain image before the acquire has signalled

    Only the final graphics submission of a frame waits for imageAvailable. When a split submitted by waitAsynchronousCompute or synchronize already carries the swap chain image's first transition of the frame, nothing orders that transition after the presentation engine has released the image. Synchronization validation reports it in both stages, with the old code as well as the new: a WRITE_AFTER_READ hazard against vkAcquireNextImageKHR, raised when a submission that does not wait for imageAvailable transitions the swap chain image. A fix would move the imageAvailable wait to the first submission whose command buffer uses the primary target. That transition's source stage would then have to be COLOR_ATTACHMENT_OUTPUT rather than TOP_OF_PIPE, so that it chains with the wait.

    RenderViewVk::splitGraphics, RenderViewVk::endFrame, RenderTargetVk::prepareAsTarget

  2. HazardSkin and deform rings advance once per view

    Skinned and deformed meshes rotate their vertex buffer rings (6 slots) at every setup, that is once per view and frame. With several views a slot comes round after fewer frames of each view than the ring was sized for. The asynchronous queue can then rewrite a slot that another view's graphics work, its velocity pass for instance, still reads; that shows as corruption rather than a fault. These rings rotate at build time, outside the backend, so the fix belongs there: skin once per world update and share the result between views, or size the rings by views.

    SkinnedMeshComponent::setupSkin, DeformMesh

  3. MinorViews share a top level structure culled by the eye

    RTWorldComponent::gatherTopLevelInstances culls instances by distance from the eye and rebuilds whenever the eye has moved. Views at different positions, and probe captures, therefore rebuild the one structure every frame, each for its own eye. A view traces against whichever build was current when its passes were recorded. That is safe now, but it is wasted work, and a view may trace against another view's culling.

    World/Entity/RTWorldComponent.cpp, RTWorldRenderer::setup

  4. MinorPipelines are still keyed by 32-bit hashes

    The graphics pipeline key uses the render pass handle, but the vertex layout and the shader are still identified by 32-bit hashes, and compute pipelines by the shader hash alone. Render passes and pipeline layouts no longer have this weakness.

    Context::validateGraphicsPipeline, Context::validateComputePipeline

Fixed

  1. FixedHazardAcceleration structure rings could be rewritten while in use

    Found after the upload changes: two views in the scene editor lost the device within seconds of moving the camera. The Aftermath dump shows a "Misaligned Address Error" in NVIDIA's internal "AS Build or Refit" shader, executing the top level build. The TLAS, its CPU-written instance data and the dynamic BLAS were 4-slot rings, sized for one view with three frames in flight. Every view, and every probe capture face, advances the shared ones, and uploads no longer block the CPU, so the asynchronous queue can trail by all frames in flight. That lets the CPU rewrite the instance data of a build that has not executed yet, which fits a fault inside the build shader.

    Now a slot is only rewritten once the frame that left it has been submitted and its epoch has completed; otherwise the ring grows (§7). Instance data lives in one buffer per slot. A run with rings started at a single slot, meant to overrun them constantly, grew them to at most five slots, with no validation messages and no fault.

    AccelerationStructureVk::advance, Context::frameSubmitted, RenderViewVk::endFrame

  2. FixedHazardUniform blocks were aged by presents, not by frames

    recycle ran from every view's present on pools shared by all views, and returned a block three presents after it was freed, which several views, or more than four swap chain images, could make premature.

    Now recycle(issuedEpoch, completedEpoch) tags freed blocks with the epoch issued by the time of the present and returns them once that epoch has completed (§10).

    Private/UniformBufferPool.cpp, Context::recycle

  3. FixedHazardThe pipeline map had no lock

    The render thread looked pipelines up for every draw and dispatch while createProgram inserted compute pipelines from loader threads into the same unguarded map.

    Now graphics and compute pipelines have maps of their own under m_pipelinesLock. A program keeps its compute pipeline and the view remembers its last graphics pipeline, so every dispatch and most draws skip the shared lookup (§11).

    Private/Context.cpp, ProgramVk, RenderViewVk::validateGraphicsPipeline

  4. FixedHazardSome layout transitions left out stages that use the image

    SHADER_READ_ONLY_OPTIMAL covered vertex and fragment shaders but not compute, and DEPTH_STENCIL_ATTACHMENT_OPTIMAL covered early fragment tests only, with write access only.

    Now sampled layouts include the compute stage and depth attachments cover early and late tests with read and write access (§12). The 20 depth and shadow-atlas hazards that synchronization validation reported in each stage with the old code are gone.

    Private/Utilities.cpp, getPipelineStageFlags, getAccessMask

  5. FixedHazardThe bindless sets used up the pool's image and buffer budget

    The three bindless sets were allocated from the program pool, leaving a single sampled image and storage image descriptor for every program set. Their variable count was also one short of the indices the allocators hand out.

    Now the bindless sets come from a pool of their own, and their variable count is 16 536 (§10).

    Context::create

  6. FixedCheckBindless descriptor writes were not serialized

    Now every write into the bindless sets goes through Context::updateBindlessDescriptors, under m_bindlessLock.

    Private/Image.cpp, Private/ApiBuffer.cpp

  7. FixedConstraintImages were not shared across queue families

    Now images with storage usage are created CONCURRENT across the graphics and compute families when those differ, so asynchronous passes may write storage textures. Render targets stay EXCLUSIVE, and binding one as a storage image in asynchronous compute is refused with an error instead of recording a transition on the wrong queue (§7).

    Private/Image.cpp, ProgramVk::validate

  8. FixedPerformanceUpload flushes and synchronous paths drained the graphics queue

    performUploads waited for its fence, as did cube and volume texture creation, TextureVk::unlock and RenderTargetVk::create, and each wait covered every earlier submission on the queue.

    Now flushes do not wait; their command buffers are released once their epoch has completed. Every initialisation path is a deferred upload, texture updates included. TextureVk::lock waits only when the GPU has not yet consumed the previous copy out of the same staging buffer (§8).

    Context::performUploads, TextureVk.cpp, RenderTargetVk::create

  9. FixedLatent bugNon-indexed indirect draws used the wrong offset and stride

    Now the non-indexed path adds drawOffset and uses the 16-byte VkDrawIndirectCommand stride. All engine callers are still indexed.

    RenderViewVk::drawIndirect

  10. FixedLatent bugVolume textures uploaded and transitioned mip 0 only

    Now every mip is staged with its own depth, copied and transitioned.

    TextureVk::create(const VolumeTextureCreateDesc&)

  11. FixedLatent bugUpdating a storage texture left it in the wrong layout

    Now a texture remembers its resting layout, GENERAL for storage textures, and updates return it there. Each side and mip also has its own part of the staging buffer, so updates of different ones queued in the same flush cannot overwrite each other's data.

    TextureVk::lock, TextureVk::unlock

  12. FixedLeakFramebuffers, render passes and command pools were never destroyed

    Now a render target set hands every cached framebuffer to deferred cleanup when it is torn down. Render passes belong to the context's cache, which destroys them, and command pools belong to their queue. The bindless set layouts, which were never destroyed, now are. setObjectDebugName no longer keeps a copy of every name it ever set for the context's lifetime.

    RenderTargetSetVk, Private/RenderPassCache.cpp, Private/Queue.cpp, ~Context

  13. FixedPlatformTimeline semaphores were used without the timeline feature

    Now Android and Raspberry Pi builds query timelineSemaphore, enable it together with VK_KHR_timeline_semaphore on devices older than Vulkan 1.2, and log an error when it is missing (§3).

    RenderSystemVk::create

  14. FixedPerformanceRead-back memory was write-combined

    Now read-back buffers are allocated GPU_TO_CPU, preferring host-cached memory.

    ApiBuffer::createReadBack, BufferReadBackVk::create

  15. FixedMinorSmall items

    • The stale note in RenderSystemVk::create that called asynchronous compute a proof of concept is gone.
    • validateComputePipeline binds only when the pipeline or the command buffer changes. Mid-frame splits reuse the command buffers of the slot's previous frame instead of allocating new ones and their fences every time.
    • changeLayout transitions a range whose subresources are in different layouts from each one's actual layout.
    • Render passes are looked up by their full specification instead of a hash, and PipelineLayoutCache compares bindings on every hit, not only in debug builds.

Kept as they are

  1. By designA wait also holds back the work recorded before it

    This was listed as a performance problem: on a dedicated compute queue the graphics work recorded before waitAsynchronousCompute or synchronize is submitted with the wait attached, so it cannot start before the batch finishes although it does not consume its results.

    Kept because it is the only thing that keeps that work from running alongside the batch (§7). Moving the wait to the next graphics submission made the Zombie main menu lose the device within seconds of the 3D scene appearing: an nvlddmkm GPU error, then VK_ERROR_DEVICE_LOST, with no validation message beforehand. Under synchronization validation, which slows everything down, the same build did not fail. With the wait back in place neither stage has failed since. Removing the stall needs a real graphics → compute dependency first.

    RenderViewVk::waitAsynchronousCompute, RenderViewVk::synchronize, RenderViewVk::splitGraphics

  2. KeptDebug labels are gated on VK_EXT_debug_marker

    The label commands come from VK_EXT_debug_utils, but labels are only recorded when the device lists VK_EXT_debug_marker, which in practice capture tools such as RenderDoc add. That makes the check a cheap "a capture tool is attached" test. Always recording labels would add a string conversion per render block for nothing.

    RenderViewVk::create, pushMarker

  3. KeptAsynchronous timestamps assume a shared timebase

    The specification only promises that timestamps written on one queue are comparable. Offsetting asynchronous timings by a graphics-queue reference query works on desktop drivers; doing it properly needs calibrated timestamps (VK_EXT_calibrated_timestamps) to map each queue's clock to the host's.

    code/Render/Frame/RenderGraph profiling, RenderViewVk::getTimeQuery

  4. KeptMaxBindlessResources is 16 536 and getTimeQuery ignores wait

    Neither is a defect. The odd bindless size is only unusual (the off-by-one variable count next to it is fixed), and time query results are one slot rotation old by design (§13), so there is nothing to wait for.

    Private/Context.h, RenderViewVk::getTimeQuery
